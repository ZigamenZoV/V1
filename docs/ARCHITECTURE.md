# Архитектура

Целевая платформа: Windows, NVIDIA GTX 1650 (4 GB VRAM, Turing TU117 — без
Tensor Cores, но с удвоенным FP16-throughput и NVDEC), HD-камеры по RTSP,
плотные сцены на входных группах. Приоритеты: стабильность 24/7, точность
счёта, максимум скорости на слабом GPU.

## Конвейер

```
RTSP-камеры ──► go2rtc/MediaMTX (fan-out, reconnect)
                      │
        ┌─────────────┴──────────────┐
        │ Capture-поток на камеру    │  NVDEC-декод сразу в разрешение
        └─────────────┬──────────────┘  инференса, latest-frame slot
                      ▼
        GPU-процесс (единственный владелец GPU)
        RF-DETR Nano FP16 (TensorRT) — батч кадров всех гейт-камер
                      │  боксы голов
                      ▼
        CPU-worker на камеру: BoT-SORT ► Zone FSM ► финализация траекторий
                      │  события enter/exit
                      ▼
        main-процесс: ReID-леджер (OSNet) ► SQLite ► Occupancy-интегратор
                      ▲                                  │
        P2PNet/LWCC-аудит (обзорные камеры) ─ коррекция ─┘
                      ▼
        FastAPI: дашборд (SSE), REST, Prometheus /metrics
```

## Ключевые решения

**Детекция голов, не тел.** Full-body детекция в толпе деградирует из-за
взаимных перекрытий; головы перекрываются на порядок реже. Вся точность
системы закладывается до трекера.

**Latest-frame policy.** Очереди кадров запрещены: capture-поток пишет кадр
в слот размера 1, инференс берёт свежайший. При просадке FPS система
деградирует по частоте, а не по задержке — для трекинга и FSM задержка
хуже пропусков.

**Один владелец GPU.** На GPU постоянно живёт только детектор. ReID —
событийная задача на CPU (единицы инференсов в минуту), аудит — плановая,
вытесняемая в паузы.

**События по завершении трека.** Событие фиксируется, когда трек потерян
окончательно: классифицируется вся траектория — первая стабильная зона,
последняя стабильная зона и факт полной последовательности A→B (вход) или
B→A (выход). Один трек — максимум одно событие. Это даёт устойчивость:

- «сунул голову и ушёл», проход мимо двери, топтание на пороге — событий
  не порождают (K-дебаунс + классификация начала/конца);
- фрагментация трека не даёт двойного счёта: обломок трека человека, уже
  прошедшего дверь, начинается в зоне B и полную последовательность не
  проходит;
- временнОй дедуп сознательно не применяется — в плотном потоке люди идут
  друг за другом чаще любого разумного cooldown.

**Occupancy = интеграл + редкие абсолютные замеры.** Σenter − Σexit копит
дрейф вечно, поэтому по обзорным камерам периодически считается вся толпа
(LWCC/P2PNet) и значение втягивается: `occ += α·(audit_ema − occ)`.
Выброс аудита применяется только после подтверждения вторым замером.
Расхождение сверх порога — алерт (камера сдвинулась, зона перекрыта,
детектор деградировал).

**ReID-леджер — корректирующий слой, не первичный счётчик.** На входе
эмбеддинг кладётся в леджер «кто внутри», на выходе гасится по
cosine-матчу с временным приором. Доля unmatched-выходов — метрика
здоровья детекта/трекинга. Ограничение: ReID по одежде ломается на
униформе.

## Процессная модель

| Процесс | Что делает | Почему отдельно |
|---|---|---|
| main | Event Store, леджер, occupancy, метрики, FastAPI, супервизор | владеет состоянием и БД |
| pc-gpu | capture-потоки, детектор, снапшоты, аудит, watchdog RTSP | единственный владелец GPU |
| pc-worker-\<cam\> | трекер + FSM + финализация одной камеры | CPU-bound, GIL обходится процессами |

Кадры из GPU-процесса в worker'ы передаются через SharedMemory-кольцо
(нужны только для ReID-кропов; отставший worker теряет кроп, но не трекинг),
детекции и события — через `multiprocessing.Queue` с drop-oldest. Кольца
создаёт супервизор — они переживают рестарты детей. Упавший дочерний
процесс перезапускается с backoff; дочерние процессы сами выходят при
смерти родителя. Режим `pipeline.mode: single` запускает те же компоненты
в потоках одного процесса (отладка, mock).

## Карта модулей

```
people_counter/
  capture/    ffmpeg+NVDEC источник (watchdog, latest-frame slot), синтетика
  detect/     Detector.infer(frames)->boxes: tensorrt | onnxruntime | mock
  track/      boxmot BoT-SORT/ByteTrack (GMC отключён) | simple (без torch)
  counting/   зоны A/B (cv2), FSM с K-дебаунсом, финализация траекторий
  reid/       OSNet-эмбеддер (ONNX, CPU) + леджер (TTL, дамп/восстановление)
  audit/      LWCC | P2PNet — интерфейс count(frame) -> float
  pipeline/   GPU-процесс, worker'ы, shm-кольцо, супервизор, сообщения
  store/      SQLite WAL: events, occupancy_log, audits
  api/        FastAPI + самодостаточный дашборд (SSE, без CDN)
```

Инференс-рантайм и трекер абстрагированы и меняются конфигом — это
запланированные пути отступления (см. риски ниже).

## Бюджет ресурсов (4 GB VRAM)

| Компонент | Где | VRAM | Когда |
|---|---|---|---|
| RF-DETR Nano FP16 engine | GPU | ~0.7–1.2 GB | постоянно |
| Батч-буферы (4 кам × 560²) | GPU | < 100 MB | постоянно |
| NVDEC-декод | GPU | ~0.2 GB | постоянно |
| Аудит (LWCC/P2PNet) | GPU | ~1 GB | по расписанию |
| OSNet x0.25, трекинг, FSM, леджер | CPU | — | — |

Ориентир RF-DETR Nano FP16 @ 560 на GTX 1650: 25–45 FPS суммарно; на
гейт-камеру достаточно 8–12 FPS → 2–4 камеры на GPU реалистичны
(`bench-detector` меряет фактический показатель).

## Ввод в строй

Каждый этап оставляет работающую систему:

1. **Видеовход**: ffmpeg в PATH, go2rtc с камерами (`deploy/go2rtc.yaml`),
   пайплайн подключается к прослойке, не к камерам напрямую.
2. **Детектор на COCO-весах** (класс person как временный):
   `scripts/export_onnx.py` → `bench-detector` → решение по разрешению/батчу →
   `scripts/build_engine.py` (строго на целевой машине: TensorRT-планы
   непереносимы).
3. **Датасет голов и файнтюн** — самый большой прирост точности:
   CrowdHuman-heads (`scripts/prepare_crowdhuman.py`) + доменные добавки
   (SCUT-HEAD, RPEE-Heads) → `scripts/train_heads.py`; затем 300–1000 своих
   кадров с целевых камер → второй файнтюн малым LR.
4. **Камеры и зоны**: `config/cameras/*.yaml`, разметка полигонов по живому
   снапшоту — `scripts/calibrate_zones.py`. Полигоны в координатах кадра
   инференса. Головы < ~12 px → `input_size: 616/672` или `roi`-кроп.
5. **Валидация счёта**: 3–5 размеченных клипов (`source: file` гоняет запись
   как живой поток), метрика — ошибка счёта за интервал. Регресс-тест при
   любой смене весов/порогов.
6. **ReID-леджер**: `scripts/export_osnet.py`, порог калибровать на своих
   данных (0.55–0.65).
7. **Аудит**: обзорная камера `role: overview`, `audit.enabled: true`,
   `pip install lwcc` (или подключить P2PNet в `audit/backends.py`).
8. **Служба Windows**: `deploy/install_service.ps1` (NSSM, автостарт,
   ротация логов).

## Риски и запасные пути

| Риск | Симптом | Fallback |
|---|---|---|
| Детектор медленный на TU117 | суммарный FPS ниже целевого | снизить разрешение → INT8 (DP4A) → лёгкий YOLO-детектор голов; интерфейс уже абстрагирован |
| TensorRT-трение на Windows | engine не собирается | `detector.backend: onnxruntime` (CUDA EP, −20–40% скорости) |
| ID-switch в дверях | скачки счёта, рост unmatched | `tracker.with_reid: true` (osnet_x0_25 в трекере) |
| CPU-узкое место | лаг worker'ов | `tracker.backend: bytetrack` (~2× дешевле), прореживание до 8 FPS |
| Дрейф occupancy | дельта аудита растёт монотонно | повысить частоту аудита, проверить зоны/камеры |
| Лицензии | закрытое коммерческое использование | RF-DETR — Apache 2.0, лицензионно чистый по умолчанию (осторожно с AGPL-детекторами при откате) |
